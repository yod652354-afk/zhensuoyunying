# ClinicOS 技术架构说明

## 1. 分层架构

```
┌─────────────────────────────────────────────────────────┐
│  前端（Vue3 + Element Plus）— 运营后台（Vite 代理 /api）  │
└───────────────┬─────────────────────────────────────────┘
                │ REST /api/v1（X-API-Key 认证）
┌───────────────▼─────────────────────────────────────────┐
│  Application 层                                          │
│   Read API（30端点·cursor分页·增量同步）                   │
│   Write API（16端点·Idempotency-Key）                    │
│   Analytics（驾驶舱/Recovery池/漏斗/质量/实验指标）        │
│   Import（CSV 患者/到店/订单）                            │
├─────────────────────────────────────────────────────────┤
│  Decision 层（services）                                 │
│   Recovery Score → 客户池 → 任务生成                     │
│   Retention 漏斗 / 超期复诊 / 今日应复诊                  │
│   Attribution：Treatment−Holdout → 增量 Lift/收入/ROI    │
│   Data Quality：完整/一致/时效/授权 四维评分              │
├─────────────────────────────────────────────────────────┤
│  Data Foundation（models 23+ 实体，统一 ID/时间戳/软删除） │
├─────────────────────────────────────────────────────────┤
│  Event 总线 + Webhook 投递器                              │
│   （事件落库 → 订阅匹配 → HMAC 签名 → 指数退避重试 → 日志） │
└─────────────────────────────────────────────────────────┘
```

## 2. 关键设计决策

### 2.1 稳定唯一 ID（规格 R-001）
- 格式：`<前缀>_<uuid4hex>`（`pat_…`、`ord_…`、`evt_…`），`app/core/ids.py`
- 手机号/姓名变更不影响 ID；所有业务对象软删除（`deleted_at`），历史归因链完整

### 2.2 统一响应与错误（规格 5.5/5.6）
- 成功：`{"data": …, "meta": {next_cursor, has_more, total, request_id}}`
- 失败：`{"error": {code, message, details, retryable, request_id}}`
- 每个请求生成 `X-Request-Id` / `X-Trace-Id`，跨系统排障

### 2.3 Cursor 分页与增量同步（规格 5.1/5.4/7）
- 固定排序 `(updated_at, <pk>)`，cursor 为 base64(updated_at, pk)
- `created_since/created_until/updated_since/updated_until` 可组合
- 支持 `include_deleted`（历史补偿）

### 2.4 幂等（规格 R-018）
- 写接口：`Idempotency-Key` 请求头 → `idempotency_records` 表，重复请求返回首次结果
- Webhook：`event_id` 唯一，同一 `(subscription, event)` 不重复投递

### 2.5 事件与 Webhook（规格 4.23/6）
- 业务动作 → `Event` 行（event_type/occurred_at/actor/object/trace_id/payload）
- 投递线程：订阅匹配（可按 event_types 过滤）→ HMAC-SHA256 签名（X-Webhook-Signature/Timestamp/Event/Id）→ 指数退避重试（`WEBHOOK_MAX_RETRIES`）→ `WebhookDelivery` 日志
- 补偿：`GET /events`（时间范围回放）+ `GET /events/replay`（重触发投递）+ 各实体 `updated_since`

### 2.6 增量归因口径（规格 9.1）
```
Incremental Lift        = Treatment Rate − Control(Holdout) Rate
Incremental Customers   = Eligible × Lift
Incremental Revenue     = Incremental Customers × 平均归因客单
ROI                     = Incremental Contribution ÷ 成本
```
实验先在 `experiment_assignments` 分组（control/treatment_a/b），`attributions` 表保存交易→触达/任务/活动/实验的追溯链。

### 2.7 认证与角色权限
- User 表 + 零依赖 JWT（HS256，PBKDF2 密码哈希）；角色 boss/staff/admin
- 前端登录 + 路由守卫；服务端调用保留 X-API-Key 认证
- 相关：`app/core/auth.py`、`app/services/auth.py`、`app/api/v1/auth.py`

### 2.8 任务闭环（自动调度 / 分配 / 反馈 / 审核）
- **每日自动调度**：APScheduler + CronTrigger（`TASK_SCHEDULE_HOUR/MINUTE`），`run_daily_tasks()` 生成 Recovery（去重）+ Retention 任务，事件 `task.daily_generated` 留痕
- **谁看诊谁负责**：`resolve_assignee()` —— 患者主诊员工 → 主诊医生 → 同门店待办最少员工（负载均衡）
- **执行反馈**：`PATCH /api/v1/tasks/{id}` 支持 feedback_note/feedback_images；图片经 `POST /api/v1/upload` 落 `/uploads/` 静态目录
- **老板审核**：`PATCH /api/v1/tasks/{id}/review` 通过/退回；退回自动回到进行中并顺延截止（催办），事件 `task.reviewed`
- 相关：`app/services/scheduler.py`、`assignment.py`、`task_engine.py`、`app/api/v1/uploads.py`

### 2.9 经营分析与运营模块
- 实验显著性（z 检验/置信区间/方向性信号）：`app/services/significance.py`
- Campaign 级归因、漏损报表、数据对账、员工激励、每周复盘：`app/services/reports.py` 等
- 内容合规扫描与审批：`app/services/compliance.py`（7 类风险规则 + 人工审批留痕）
- 话术模板库：`app/services/templates.py`（渠道 × 任务类型 × 变量渲染）

## 3. 数据库（PostgreSQL 切换）

所有模型使用 SQLAlchemy 2.0 声明式（`Mapped`/`mapped_column`），枚举 `native_enum=False`、JSON 用通用 `JSON` 类型，**SQLite ⇄ PostgreSQL 零改动切换**：

```
DATABASE_URL=postgresql+psycopg://user:password@host:5432/clinicos
```

## 4. 部署建议（生产）

- 用 Alembic 管理迁移（当前 MVP 用 `Base.metadata.create_all`）
- `WEBHOOK_DELIVERY_MODE=http` + 独立投递队列（当前为进程内守护线程，适合单实例）
- 多租户：全部业务表含 `organization_id/store_id`，API 按组织/门店过滤（规格 R-004）
- 安全合规（PIPL）：数据最小化、DNC 全局生效、营销内容审批留痕——正式商用前需专业法律/安全审查（见项目计划书 §13）

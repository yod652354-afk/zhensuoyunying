# RevOS 一次性修复与继续开发要求

## R-01 修复对照组自然结果

### 当前错误

可信业务事件同步时跳过control机会，导致对照组自然预约、到店和支付不进入Outcome；实验指标又依赖Opportunity.WON，造成control转化率被压低。

### 正确模型

```text
CustomerFact
  ├─ Treatment：允许触达，记录自然+干预后结果
  └─ Control：禁止触达，但完整记录自然结果
```

### 实现要求

- 所有组均保存可信业务事实；
- 对照组Outcome标记`organic/control_observation`，不得关联Touch/Action收入贡献；
- 对照组的预约、到店、支付必须进入实验指标；
- Opportunity状态可根据自然结果变化，但归因模型明确区分organic与intervention；
- `experiment_metrics`两组使用同口径、同观察窗口、同主要指标；
- 退款在窗口内反向修正净收入；
- 禁止把Treatment全部收入称为增量收入。

## R-02 统一每日自动运营链

### 当前错误

Scheduler直接调用旧Recovery/Retention创建Task，绕过Opportunity、仲裁、ExecutionPlan和人工审核。

### 新链路

```text
数据增量同步/补偿
→ Customer State重算
→ Future/Current/Past Detectors
→ Opportunity去重和过期
→ Arbitration
→ Decision
→ ExecutionPlan候选
→ AI内容和自动检查
→ 待人工审核
```

### 要求

- Scheduler不得直接创建外部触达Task；
- 旧`generate_recovery_tasks`和Retention任务接口只能作为兼容入口，并内部转换为统一Opportunity流程，或显式禁止生产使用；
- 同一客户同周期只产生一个主要外部计划；
- 每个组织、每个门店分别运行，不得只处理数据库第一条Organization；
- 每租户记录运行统计、错误、游标和重试状态；
- 单次失败不得阻断其他租户。

## R-03 移除浏览器API Key

- 删除上传、导入和路由守卫中的API Key认证分支；

## R-04 客户事实与机会归因分层

### 当前错误

同一patient的可信事件会写入全部活动Treatment机会，一笔支付可能令多个机会WON。

### 新模型

```text
BusinessFact（事实，只存一次）
→ OpportunityOutcomeLink（机会结果映射）
→ Attribution（收入贡献）
```

### 匹配条件

- organization/store/customer一致；
- 事件发生在机会/计划归因窗口内；
- 主ExecutionPlan或有效Touch存在；
- Touch早于Outcome；
- scenario允许该Outcome；
- 排除已过期、抑制和非主计划；
- 同一事实只能有一个primary opportunity；
- 其他机会可以记录辅助关联，但不得重复计算收入。

### 要求

- 增加BusinessFact或等效的不可重复事实层；
- 保存匹配原因、匹配版本和置信度；
- 无法确定时进入待人工归因，不得自动广播；
- 支付、退款、订单和Outcome可追溯。

## R-05 数据库完整性与并发幂等

新增migration，不修改旧migration。

至少建立：

- CustomerIdentity有效身份唯一约束；
- 同客户/场景/周期活动Opportunity唯一约束；
- BusinessFact源系统/事件ID唯一约束；
- Outcome机会/类型/源事件唯一约束；
- ContentDraft机会/版本唯一约束；
- ExecutionPlan机会/版本唯一约束；
- StrategyVersion组织/类别/代码/版本唯一约束；
- InteractionSession token_hash唯一约束；
- MpEvent event_id唯一约束；
- Action幂等键唯一约束；
- 关键父子ForeignKey，或明确的跨数据库完整性机制。

SQLite和PostgreSQL均需验证；唯一冲突应转换成幂等返回或409，不得500。

## R-06 完成企微状态闭环

- 正确区分“群发任务已创建”“等待成员确认”“已发送”“送达未知”“失败”；
- `add_msg_template`成功不得直接标记为SENT，除非真实接口语义确认已经发送；
- 保存msgid及成员发送任务标识；
- 实现回调接收、验签、幂等和状态更新；
- 如官方只支持结果查询，接入查询接口；
- 无查询能力时提供员工人工确认＋后续业务结果兜底，但状态不得伪造为delivered；
- UNKNOWN状态禁止自动重发；
- token失效必须真实刷新后重试一次；
- 错误码和频控以真实接口契约为准；
- 真实凭证缺失时完成Mock server契约测试。

## R-07 生产持久任务与Outbox

当前进程内scheduler/worker不满足一次性完整开发要求。

实现数据库Outbox＋持久Job最小方案，或项目已有条件下使用成熟队列。必须具备：

- 任务持久化；
- 多实例唯一领取；
- lease/heartbeat；
- 指数退避；
- 最大重试；
- 死信；
- 人工重放；
- 每租户限流；
- 状态查询；
- 失败告警接口；
- 应用重启后继续；
- 业务事务与事件发布一致性。

不得依赖单进程后台线程保证关键触达和状态重算。

基于已下发诊所SaaS API合同实现通用Connector运行框架：

- OpenAPI/字段映射配置；
- 全量首导；
- `updated_since + cursor`增量同步；
- Webhook实时事件；
- 丢失事件补偿；
- 删除/退款/取消；
- 每日患者、到店、订单、支付、退款对账；
- 租户独立同步游标；
- 错误隔离和重放；
- 原始敏感数据最小化；
- Connector契约测试和模拟诊所SaaS服务。

不得把“API已要求前端提供”等同于RevOS自动采集已经实现。
